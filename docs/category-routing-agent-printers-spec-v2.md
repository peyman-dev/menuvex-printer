# مشخصات نسخهٔ ۲ — مسیردهی دسته‌بندی محصول به پرینتر (سازگار با پرینترهای Agent)

**قرارداد: نسخهٔ ۲** — پیشوند همهٔ APIها: `/api/v1`
**صفحهٔ کاربر:** `/dashboard/settings/printers/categories`
**برای:** **ایجنتِ فرانت (سایت)** + **ایجنتِ بک‌اند (سرور)** — هر دو

> **این سند را به هر دو ایجنت بدهید.** هر کدام بخشِ خودش را پیاده می‌کند و **این سند قراردادِ مشترکِ دو طرف است** — اگر یکی از دو طرف آن را رعایت نکند، داده‌ها با هم ناهماهنگ می‌شوند.
>
> نسخهٔ ۱ (v1) همین سند را هم در اختیار هر دو ایجنت بگذارید؛ v2 جایگزینِ بخش‌هایی از v1 می‌شود که در «تغییرهای v2» (بخش ۰) آمده‌اند.

---

## ۰. تغییرهای v2 نسبت به v1 (خلاصهٔ اجرایی)

| # | تغییر | چرا |
|---|---|---|
| 1 | پرینترِ مقصد می‌تواند **پرینترِ Agent** باشد — پرینترهایی که در **دستیارِ MenuVex** (Agentِ دسکتاپ — «MenuVex Printer Agent») تعریف شده‌اند و با `printer:<uuid>` شناسایی می‌شوند | در حالت `menova-print-method = agent` پرینترها در Agent تعریف می‌شوند، نه در سرور |
| 2 | مسیرها (routes) **همیشه در بک‌اند** ذخیره می‌شوند — در حالت agent دیگر «فقط در مرورگر» نیستند | مسیرها باید بین دستگاه‌ها و کاربران مشترک باشند |
| 3 | مدلِ مقصدِ پرینتر تغییر کرد: `printer_targets: [{ printer_ref, printer_name, printer_source }]` — و `printer_ids` (UUIDهای سرور) برای سازگاریِ قبلی نگه داشته می‌شود | بک‌اند پرینترهای Agent را نمی‌شناسد؛ آن‌ها را به‌صورتِ مرجع (ref) ذخیره می‌کند |
| 4 | سیاستِ گردشِ چاپ (policy) می‌تواند مقصدِ پیش‌فرضِ آشپزخانه را به‌صورتِ refِ Agent هم بپذیرد | fallback در حالت agent باید به پرینترِ Agent اشاره کند |
| 5 | چاپ در حالت agent از طریقِ Agent (SDK) است؛ بک‌اند چاپ نمی‌کند و هیچ بایتِ ESC/POS نمی‌گیرد | مسیرِ فیزیکی همان قراردادِ Agent است |

**v2.1 (اصلِ ایمنی — amendment):** بخش ۱ — اگر همهٔ مقصدهای یک قانون پیدا‌نشده باشند، آن دسته به fallback می‌رود + هشدار; اقلام هرگز گم نمی‌شوند.

## ۱. رفتار و محدوده

مدیر کافه برای هر دسته‌بندی یک قانون می‌سازد؛ مثلاً:

- «قهوه» → پرینتر بار
- «غذا» → پرینتر آشپزخانه
- «نوشیدنی سرد» → پرینتر بار **و** پرینتر تحویل سفارش

**قواعد:**

1. هر دسته‌بندی در هر کافه حداکثر **یک قانون** دارد.
2. هر قانون حداقل یک مقصدِ پرینتر دارد و می‌تواند چند پرینتر را انتخاب کند.
3. مقصد می‌تواند **پرینترِ سرور** (رکوردِ فعال در `/printer-configs` — حالت QZ) یا **پرینترِ Agent** (شناسهٔ `printer:<uuid>` در دستیار — حالت agent) باشد.
4. چند دسته که به یک پرینتر وصل‌اند، در یک بلیتِ سفارش برای همان پرینتر گروه می‌شوند. اگر یک دسته به دو پرینتر وصل باشد، اقلام همان دسته روی هر دو چاپ می‌شوند.
5. قانونِ غیرفعال در محاسبهٔ مقصد نادیده گرفته می‌شود.
6. این قابلیت فقط بلیتِ اقلام/آماده‌سازی آشپزخانه را مسیردهی می‌کند؛ **فاکتور صندوق/مشتری طبق قراردادِ قبلی و مقصد صندوق چاپ می‌شود.**
7. مسیرِ چاپ فیزیکی همان چیزی است که در قراردادِ روشِ چاپ آمده (مرورگر، WebUSB، QZ Tray یا Agent). بک‌اند فقط تنظیمات را نگه می‌دارد و فرض نمی‌کند به USB/LAN محلی دسترسی دارد.

### سیاستِ دسته‌های بدون قانون

- اگر هیچ قانونِ فعالی در کافه نیست → رفتار legacy: یک بلیتِ کاملِ آشپزخانه به مسیرِ معمولِ چاپ POS می‌رود.
- اگر دست‌کم یک قانونِ فعال هست، دسته‌ای که قانونِ فعال ندارد (یا فقط مقصدِ پیدا‌نشده دارد) به ترتیب به مقصدِ پیش‌فرض می‌رود:
  1. `PrintWorkflowPolicy.preferred_kitchen_printer_id` — که حالا می‌تواند **UUIDِ سرور یا refِ Agent (`agent:printer:<uuid>`)** باشد — اگر در روشِ فعلی پیدا شود؛
  2. اولین پرینترِ فعال با نقشِ `kitchen` (در حالت QZ از فهرستِ سرور؛ در حالت agent از فهرستِ Agent);
  3. انتخابِ معمولِ پرینترِ آشپزخانهٔ POS.
- اگر برای یک دسته قانونِ فعال و مقصدِ پیدا‌نشده وجود داشته باشد، فقط همان مقصدها اقلام آن دسته را می‌گیرند؛ به پیش‌فرض کپی نمی‌شوند.
- **اصلِ ایمنی (v2.1):** اگر **همهٔ** مقصدهایِ یک قانونِ فعال پیدا‌نشده باشند، آن دسته مانندِ «دستهٔ بدونِ قانونِ فعال» به fallback می‌رود **+ هشدارِ قابلِ مشاهده**. اقلامِ آشپزخانه **هرگز** گم نمی‌شوند. این، جایگزینِ «فقط همان مقاصد» در v2 است.

*(مقصدِ پیدا‌نشده = پرینترِ متناظر در روشِ فعلی پیدا نمی‌شود.)*

## ۲. قراردادِ داده — مدلِ «مرجعِ پرینتر» (v2)

```json
{
  "id": "route-uuid",
  "category_id": "category-uuid",
  "category_title": "قهوه‌های گرم",
  "printer_targets": [
    {
      "printer_ref": "agent:printer:7be80e8c-3d6a-42cf-973f-750ab6d3dd45",
      "printer_name": "صندوق فروش",
      "printer_source": "agent"
    },
    {
      "printer_ref": "b3f1c2d4-0000-0000-0000-serveruuid",
      "printer_name": "POS 80",
      "printer_source": "backend"
    }
  ],
  "is_active": true,
  "created_at": "2026-10-05T10:30:00Z",
  "updated_at": "2026-10-05T10:30:00Z"
}
```

- **`printer_ref`** — مرجعِ پایدارِ پرینتر:
  - **پرینترِ Agent**: `agent:printer:<uuid>` — UUID همان شناسهٔ پرینتر در Agent است (همان `printer:<uuid>` که `printers.list` می‌دهد). پیشوندِ `agent:` آن را از UUIDهای سرور متمایز می‌کند.
  - **پرینترِ سرور**: همان UUIDِ جدولِ `printer_configs`.
- **`printer_source`** — `"agent"` یا `"backend"` — از روی ref هم قابلِ تشخیص است، ولی صریح ذخیره می‌شود.
- **`printer_name`** — snapshotِ نمایشی که هنگامِ نوشتن ذخیره می‌شود. **ref authoritative است؛ نام فقط یک snapshot است.** وقتی فرانت بتواند آن ref را در فهرستِ زندهٔ Agent پیدا کند، نامِ زنده را نشان می‌دهد (دقیقاً همان‌طور که هست)؛ وگرنه snapshot را با هشدار نشان می‌دهد.
- **سازگاریِ قبلی**: پاسخ همچنین `printer_ids: [<UUIDهای سرور>]` را دارد (فقط مقصدهای backend) — فرانتِ قدیمِ v1 کار می‌کند. درخواست هم `printer_targets` (v2) و هم `printer_ids` (v1 — معادلِ backend refs) را می‌پذیرد.

### الزاماتِ یکپارچگی (v2)

- `category_id` متعلق به tenantِ درخواست‌کننده باشد.
- `printer_ref`ها در یک مسیر یکتا باشند؛ حداقل یک مقصد.
- **مقصدهای backend** باید رکوردِ فعالِ `printer_configs` همان tenant باشند (مثل v1).
- **مقصدهای agent** باید از الگوی `^agent:printer:[0-9a-f-]{36}$` پیروی کنند — بک‌اند آن‌ها را **اعتبارسنجیِ وجودی نمی‌کند** (نمی‌تواند — Agent صاحبِ پرینترهاست) و به‌صورتِ opaque ذخیره می‌کند.
- یک قانون برای همان `(tenant_id, category_id)` → دومی `409 CONFLICT`.
- جایگزینیِ مقصدها در PUT/PATCH اتمیک است (یک transaction).
- حذف/غیرفعال‌سازیِ پرینترِ سرور → cascade/detach (مثل v1). **پرینترِ Agent که پاک شود، کارِ بک‌اند نیست** — مسیر ref را نگه می‌دارد؛ فرانت هشدار می‌دهد و در چاپ ردش می‌کند.

## ۳. API — CRUD (همان endpointها، مدلِ v2)

مسیرِ پایه: `/api/v1/printer-configs/category-routes`

### ۳.۱ GET — فهرست

- `?is_active=true|false` اختیاری؛ فهرستِ خالی → `200` با `[]` (هیچ‌گاه 404).
- آیتم‌های پاسخ: مدلِ v2 (با `printer_targets` و `printer_ids`).

### ۳.۲ POST — ساخت

بدنهٔ v2:

```json
{
  "category_id": "category-coffee-uuid",
  "printer_targets": [
    { "printer_ref": "agent:printer:<uuid>", "printer_name": "صندوق فروش", "printer_source": "agent" }
  ],
  "is_active": true
}
```

- بدنهٔ v1 (`printer_ids`) هم پذیرفته می‌شود → معادلِ backend refs.
- پاسخ `201` با مدلِ کامل.

### ۳.۳ GET /{id} / ۳.۴ PUT / ۳.۵ PATCH / ۳.۶ DELETE

همان semanticsِ v1 با مدلِ v2؛ PATCH جزئی است (فقط فیلدهایِ حاضر).

### ۳.۷ Policy — `GET/PUT /printer-configs/policy`

- `preferred_kitchen_printer_id` می‌تواند UUIDِ سرور **یا** refِ Agent (`agent:printer:<uuid>`) باشد.
- پاسخ شاملِ `preferred_kitchen_printer_name` و `preferred_kitchen_printer_source` (snapshot) است.

### ۳.۸ کدهای وضعیت

همان v1: `200` / `201` / `401` / `403` / `404` / `409` / `422`.

## ۴. اعتبارسنجی و خطاها

- `422`: category نامعتبر، ref با الگوی نادرست، فهرستِ مقاصد خالی، مقصدِ backendِ غیرفعال، مقصدِ تکراری.
- `409`: قانونِ تکراری برای همان دسته.
- `404`: route/category/printerِ tenantِ دیگر.
- پیامِ خطا فارسی و کاربرپسند است (مثل v1).

---

## ۵. بخشِ بک‌اند — کاری که ایجنتِ بک‌اند باید پیاده کند

1. **Migration**: به جدولِ targetها ستون‌های `printer_ref` (text)، `printer_name` (text) و `printer_source` (text) را اضافه کن. backfill: ردیف‌های موجود → `source=backend`، `printer_ref = printer_id`، `printer_name = نامِ پرینتر`. ستونِ قدیمی `printer_id` (FK) را نگه دار (nullable) — یک مقصد یا با `printer_id` (backend) یا با `printer_ref` با پیشوندِ `agent:` (agent) معتبر است.
2. **CRUD** با مدلِ v2 + سازگاریِ قبلی (`printer_ids` را بپذیر؛ هر دو شکل را در پاسخ بده).
3. **اعتبارسنجی** طبق بخش ۲ و ۴ — backend refs را با `printer_configs` چک کن؛ agent refs را فقط از نظرِ الگو (format) چک کن.
4. **Policy**: refِ Agent را برای مقصدِ پیش‌فرضِ آشپزخانه بپذیر.
5. **Orders**: `GET /orders/{id}` اقلام با `category_id` (مثل v1) — بدونِ تغییر.
6. **print-jobs**: `printer_key` = `printer_ref`ِ مقصد (مثلاً `agent:printer:<uuid>`) است؛ کلیدِ idempotency: `(tenant_id, order_id, printer_key, doc)`.
7. **هرگز چاپ نکن و بایتِ ESC/POS نپذیر** (مثل v1).
8. **تست**: چک‌لیستِ بخش ۱۱ — شامل حالت‌های refِ Agent.

---

## ۶. بخشِ فرانت — کاری که ایجنتِ فرانت باید پیاده کند

1. **صفحهٔ مسیرها — هر دو روش**: در حالت `agent` پرینترهایِ قابلِ انتخاب، پرینترهایِ **Agent** هستند (از `client.getPrinters()` — نام‌ها دقیقاً همان‌طور که هستند، وضعیتِ زنده). در حالت QZ پرینترهایِ سرور. **یک پرینترِ Agent هرگز پیامِ «در سرور ثبت نشده» نمی‌گیرد.**
2. **ساخت/ویرایش**: دسته از بک‌اند (`GET /categories`) + مقصدها (در حالت agent: پرینترهای Agent — ref به‌صورتِ `agent:printer:<uuid>` و نامِ زنده به‌عنوان snapshot) → POST/PUT/PATCH به بک‌اند. **هیچ دادهٔ مسیر را در مرورگر ذخیره نکن** (ذخیره‌سازیِ browser-localِ فعلی را بردار).
3. **خواندن و تطبیق**: مسیرها را از بک‌اند بخوان؛ هر مقصد را تطبیق بده: refهای `agent:` را با فهرستِ زندهٔ Agent (با id — پیشوندِ `agent:` را برای SDK بردار) و refهای backend را با فهرستِ سرور (در حالت QZ). اگر تطبیق شد، نامِ زنده را نشان بده؛ اگر نشد، snapshot + هشدار («این پرینتر دیگر در دسترس نیست»).
4. **جریانِ چاپ (agent)**: اقلامِ سفارش (بک‌اند) → گروه‌بندی بر اساس `category_id` → مسیرهای فعال → تطبیق در روشِ فعلی → برای هر مقصد: بلیتِ آشپزخانه را با Agent چاپ کن (مسیرِ فیزیکی طبق `menova-print-method`). فاکتورِ صندوق بدونِ تغییر.
5. **مقصدِ پیدا‌نشده**: در چاپ رد می‌شود + هشدار؛ دسته‌ای که همهٔ مقاصدش پیدا‌نشده است → fallback (بخش ۱).
6. **قانونِ نام**: ref authoritative است؛ snapshot هر وقت که فرانت پرینتر را پیدا کرد، به‌روز می‌شود.
7. **Agentِ خاموش**: صفحهٔ مسیرها همچنان کار می‌کند (خواندن/نوشتن از بک‌اند — بدونِ نیاز به Agent)؛ فهرستِ پرینترها snapshotها را با راهنمای «دستیار خاموش است» نشان می‌دهد (طبق قراردادِ روشِ چاپ).
8. **تست**: چک‌لیستِ بخش ۱۱.

## ۷. قوانینِ SYNC — هماهنگیِ دو طرف

1. **بک‌اند، منبعِ واحدِ ROUTES است** — مشترک بین دستگاه‌ها و کاربران. فرانت در هیچ حالتی مسیر را در مرورگر ذخیره نمی‌کند.
2. **Agent (دستیارِ دسکتاپ)، منبعِ PRINTERهاست** (در حالت agent) — فرانت از SDK می‌گیرد (`getPrinters`) — نام‌ها دقیقاً همان‌طور که هستند.
3. **بک‌اند، منبعِ CATEGORIES و ORDERS است.**
4. **فرانت، منبعِ تطبیقِ لحظهٔ چاپ است** (category → target → پرینترِ فیزیکی).
5. **ref قرارداد است**: `agent:printer:<uuid>` (agent) / UUIDِ سرور (backend). هر دو طرف ref را دقیقاً ذخیره و مقایسه می‌کنند — بدونِ normalize یا حذفِ پیشوند در سمتِ بک‌اند.
6. **نام یک snapshot است**: هر وقت فرانت پرینتر را پیدا کرد، به‌روز می‌شود؛ در غیر این صورت فقط برای نمایش است. renameِ پرینتر در Agent مسیر را خراب نمی‌کند (ref ثابت می‌ماند).
7. **حذفِ پرینترِ Agent** مسیرها را پاک نمی‌کند (بک‌اند خبر ندارد) — فرانت هشدار می‌دهد و در چاپ رد می‌کند. حذفِ پرینترِ سرور cascade می‌شود (مثل v1).
8. **هر دو ایجنت همین قرارداد را پیاده می‌کنند** — شکلِ API، کدهای وضعیت، الگوی ref — هر انحرافی یعنی باگِ همان طرف.
9. **حالت QZ بدونِ تغییر است** (v1) — مدلِ v2 با v1 سازگار است.

---

## ۸. جریانِ چاپ در حالت agent

1. سفارش با `GET /orders/{id}` خوانده می‌شود؛ اقلام به مدلِ رسید تبدیل می‌شوند.
2. قوانینِ کافه از `GET /printer-configs/category-routes` خوانده می‌شود (cache/dedupeِ ۵ ثانیه‌ای در لایهٔ server-action مجاز است).
3. اگر قانونِ فعالی نیست → مسیرِ legacyِ تک‌بلیت.
4. در غیر این صورت اقلام بر اساس `category_id` و `printer_targets` گروه‌بندی می‌شوند؛ برای هر پرینترِ unresolved یک بلیت ساخته می‌شود.
5. مقصدِ فیزیکی با `printer_id` (idِ خامِ Agent — بدونِ پیشوند) به لایهٔ چاپِ همان روش داده می‌شود (Agent SDK / QZ / WebUSB — per `menova-print-method`).
6. هر موفقیتِ چاپ با `POST /pos/print-jobs` ثبت می‌شود — `printer_key` = `printer_ref`ِ مقصد، `doc="kitchen"`، `status="printed"`.
7. فرانت به بک‌اند هیچ بایتِ ESC/POS نمی‌فرستد.

---

## ۹. حالت QZ (legacy) — بدونِ تغییر

همان رفتارِ v1؛ مدلِ v2 با v1 سازگار است (فرانتِ قدیم `printer_ids` را می‌خواند).

## ۱۱. چک‌لیستِ پذیرش (Definition of Done)

- [ ] migration و قیدهای tenant-safe اعمال شده‌اند.
- [ ] GET در حالتِ خالی `200` با `[]` می‌دهد.
- [ ] POST/GET/PUT/PATCH/DELETE با شکل‌های v2 کار می‌کنند.
- [ ] `PATCH {"is_active": false}` فقط همان فیلد را تغییر می‌دهد.
- [ ] refهای Agent بدونِ اعتبارسنجیِ وجودی پذیرفته می‌شوند؛ ref با الگوی نادرست → `422`.
- [ ] refهای backend همچنان اعتبارسنجی می‌شوند (غیرفعال → 422؛ tenantِ دیگر → 404).
- [ ] چند مقصد پشتیبانی می‌شود؛ حداقل یک مقصد اجباری است.
- [ ] یک قانون به ازای هر دسته (409 در تکرار).
- [ ] صفحهٔ فرانت در حالت agent پرینترهای Agent را نشان می‌دهد (نامِ دقیق، وضعیتِ زنده) — بدونِ پیامِ «در سرور ثبت نشده».
- [ ] فرانت هیچ دادهٔ مسیر را در مرورگر ذخیره نمی‌کند.
- [ ] چاپ: گروه‌بندیِ دسته → تطبیق → چاپ با Agent؛ مقصدِ پیدا‌نشده با هشدار رد می‌شود.
- [ ] فاکتورِ صندوق بدونِ تغییر.
- [ ] fallback کار می‌کند (بدون route → legacy؛ دستهٔ بدون route → policy / اولین آشپزخانه / پیش‌فرض POS).
- [ ] renameِ پرینترِ Agent → مسیرها کار می‌کنند (ref ثابت)، نامِ زنده نمایش داده می‌شود.
- [ ] حذفِ پرینترِ Agent → هشدار + رد در چاپ؛ مسیرها می‌مانند.
- [ ] حالت QZ بدونِ تغییر (تست‌های v1 سبز).
- [ ] جداسازیِ tenant (همهٔ حالت‌ها).
- [ ] لاگ `POST /pos/print-jobs` به تفکیک `printer_key = printer_ref`; idempotency = `(tenant, order, printer_key, doc)`.
- [ ] tsc / eslint / تست‌ها در هر دو طرف سبز.
